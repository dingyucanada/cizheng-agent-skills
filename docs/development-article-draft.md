# 从鉴定按钮到陶瓷证据研究工作台：瓷证的开发记录


最新完整第05轮已实际失败：4次模型、10次工具、服务端136.052秒。两张原图产生实际观察，协调器按本轮观察加载青花方法；下一主动作90秒超时，没有AI报告、该报告的NAT核查、StepFun反证或修订导出。固定文字格式合成探针也90秒超时，155.686秒晚到结构合格记录只按独占窗口关联。当前ARM开发源码129项流程CPU合同通过，不能替代以上业务失败。最新版本和证据见[当前状态](../STATUS.md)、[第05轮](../verification/nvidia/compact-workflow-05/README.md)。

本篇尚未在赛事技术社区发布，更新至2026-09-28。官方“十日谈”是赛事栏目名，不表示项目已经开发十天；本文记录实际研究、设计、开发、NVIDIA集成与Spark联调。没有完成的专业专家验收不写成成果。

## 业务决定结构

最初方案围绕轻量预审和大模型陶瓷鉴定。研究 Jev 与 Laya 后，我们没有把浏览器智能体或文字路由框架当作本地视觉识别权重，也没有继续承诺原生真伪、AI生成概率。图片清晰、知识检索有出处和模型输出自信，都不能自动证明器物真实。

专业用户的问题比“这是什么年代”更具体。博物馆需要登记对象、核对文献和状况，收藏者需要整理来源凭据，拍卖图录需要区分归属措辞和物理状况。实际阅读 MuseumPlus 产品册、Artlogic 官方工作流、Christie’s 和 Sotheby’s 说明，以及 Getty CDWA 来源史规范后，我们把对象记录、可见现象、材料记载和归属意见分开。没有登录同行客户后台，没有访谈这些机构，也不把产品宣传当成使用测试。

新版采用六个工作区：案件总览、器物档案、图像研究、知识资料库、研判与补证、报告复核。深色导航、浅色研究桌和证据检查器让当前任务与旁证同时可见。原照底片带、双图、缩放和人工区域记录用于真图操作，不画假的AI热点。三个角色改变采集与交付重点，不能被当作机构身份。

## RAG与Skills各自承担什么

知识库保存可回查的出处和正文，Skill保存执行方法与适用边界。25条项目资料是项目原创短摘要，参考 V&A、CCI、Getty、Met 和特定版本拍卖术语。它们不是完整陶瓷断代库，未经过原机构或专家审定。未知文字权利只登记出处，不能自动抓整本书或把全部官网文章视为开放许可。

本地 SQLite 索引支持中文重叠双字词，检索分是文字相关性，不是可靠性。运行开始时固定资料快照，真正引用还要经过读取段落与版本、文档哈希、段落哈希和locator校验。公开馆藏的时期标签只属于该编号对象，不成为未知器物的答案。

七个自研Skill包按描述、正文、参考资源渐进加载。通用编目与来源核查加入原先的器类路由、青花花觚比较、状况假说和补证修订；每个包有整包哈希和真实审核状态。我们学习官方材料中工具、方法和运行框架的分工，不伪造NVIDIA Verified或专家签名。

## 可交接的材料工作

没有视觉模型也应能工作。原照归档、区域人工观察、已获许可文字、来源事件和状况检查都可以独立登记。来源事件区分上拍、出版、展览、流转和缺口，保存每项记载与本器物的联系依据。“有凭据定位”只表示资料可找回，不证明历史事件发生。PDF保留原文件和目录，尚未OCR。许可TXT可在文字凭据任务中分段读取，引用必须对应实际已读回执；附件中的文字始终作为待核查材料，不作为系统指令。

准备档案输出JSON、Markdown和可打印HTML，保留图像哈希、来源版本、记录限制和人工复核。准备资料复核绑定案卷版本，模型意见复核绑定已完成运行；两者分别保留，更改材料后旧复核过期。单人本机操作人的身份没有认证，不能直接变成机构审批。

## 反例比评分有用

真实浏览器验收发现，初始化早于选案的知识列表会错误禁用关联按钮；修复让按钮随当前案更新，不丢检索上下文。独立初审还复现了更严重的问题：来源库改到r2后，仍为同一案卷版本导出的准备档案悄悄读取r2。这个初版被硬门槛拒绝，而不是靠其他优点抵消。修订后按实际显示的文档revision/hash关联，显式更新才推进案卷；可变的全库索引信息也不混入固定材料包哈希。

另一个反例是可读准备档案只展示资料前四段，命中的后续段落会消失。现在完整输出已关联授权段落及校验标识，并与JSON核对。所有工程测试、失败反例与版本记录保留；纯色图、脚本模型和模拟网络只能证明协议，不能算陶瓷鉴定样本。

## 把NVIDIA技术落到可复现的工具

为了对齐平台评分，我们没有把技术名称写进架构图就算使用。NVIDIA NeMo Agent Toolkit 1.9通过正式包入口注册检索与核查工具，Builder组合真实工作流，CLI执行和三个引用合同评测均保留输出。专业工作台调用独立Toolkit环境核对指定历史报告；即使资料库后来更新，也按当时快照及阅读回执核查。这个流程没有模型调用，1.0合同均分表示三个软件预期都满足，不是鉴定准确率。

NVIDIA SkillSpector 2.12对七个运行技能完成无模型静态扫描。按官方Tier-1暂存规范排除评估目录，范围内没有发现；完整包中的评估脚本文件读取诊断仍保留。静态检查、方法效果评测、签名和NVIDIA Verified是不同步骤，我们没有把扫描结果变成认证。

实际联调又暴露两个容易漏掉的问题：文字凭据报告使用`evidence_refs`，通用核查不能只读视觉报告的引用字段；历史报告导出不能因为页面切换就混入当前版本。分别以实际API、Toolkit子进程和浏览器状态回归后，NVIDIA核查记录才进入对应报告的可读导出。

实际增加的NAT profiler按官方`track_function`包裹检索、核查和工作流，启用嵌套分析并保存全部事件。三个公开软件样例产生42条事件、9个SPAN与9个FUNCTION，生成ATIF、CSV、Gantt和指标，0模型调用、0联网尝试。原图的18行同时包含内部SPAN和外部FUNCTION，不能相加为18次业务动作；测量的是CPU引用工具，不能当作主视觉或GPU性能。原始与公开文件SHA、源码和运行版本一起保留，便于复现。[真实profiler记录](../verification/nvidia/nat-profiler-01/README.md)

## Spark首次真实生成的失败与修复

节点是ARM64的NVIDIA GB10。官方容器与Hugging Face下载通道未能及时完成，我们选择Qwen官方ModelScope权重和PyTorch官方CUDA13 ARM64轮子，所有文件逐一记录SHA。2B功能候选11个文件约4.27GB，不把它当陶瓷效果排名。新版冻结后端在节点实际通过342项工程检查。

真实FP32/BF16矩阵计算与GPU模型加载通过后，第一次生成仍全部失败：节点缺少Python.h，而PyTorch原生GPU小矩阵运算触发Triton编译。关闭TorchDynamo没有解决这个原生运算路径。我们在项目内刷新独立官方签名索引、验证并解压Python开发头文件，只给视觉进程增加include路径，不安装系统软件或升级解释器。原始失败和包来源、哈希、修复步骤继续保留。

修复后真实文字JSON和单图探针通过，双图也成功生成，却复制了提示里的颜色选项，语义合同失败。这个反例说明部署成功和模型胜任任务不同。服务健康检查因此增加实际合成图生成预热；业务质量仍要另做完整工具流程和较大模型比较，不能修答案或把已知馆藏标签算成预测。

## 从GPU生成到工具任务的第二道验收

8B候选约17.55GB，四个权重分片逐一交叉核验Qwen官方仓库LFS指针；GPU生成预热和原有文字、单图、双图顺序探针均通过。主Agent仍可能失败：旧版同一公开双照片任务执行7次模型、6次工具后，局部GPU生成139.255秒超过客户端90秒上限。两条已经通过结构校验的观察只是“直接可见现象”模板，不能算有效专业细节。服务端记录185.915秒和客户端轮询195.210秒分别描述不同范围，不能相互替代。

我们由此修订协议：给实际图片ID生成合法JSON Schema，每张图先记录一条简短综合观察，细节用局部查看；宿主拒收上述模板句，视觉输出限800 tokens，动作仍限2500。工具结果压缩时保留可信、实际加载的方法正文，防止模型丢掉Skill后重复加载；连续错误可修复一次，成功动作之后才重新获得修复机会。每轮12次模型、20次工具、300秒以及每次90秒的限制保持不变。

当时的开发源码576项工程检查通过。它们验证输出约束、模板拒收、方法保留与失败日志，并不证明8B业务质量。真实照片第03轮已产生两条具体描述，但主动作必填字段和维度校验连续失败；随后加入严格有界的结构约束解码，真实GPU格式探针通过；但公开两图full-workflow01在12次模型、16次工具、207.586秒后耗尽预算，没有报告。全部响应stop，格式合格并未解决工具规划问题。输入、模型和协议的每次变化均单独记录，不能把这次协议变更称为纯模型对照或已测出的Skills增益。

受控准备实验先通过原工具读本案方法、固定正文和真实原照；主模型仍自行判断。第02轮两次模型、七次工具，但主动作90秒超时，GPU在133.981秒后才生成1029个输出tokens。格式合格不等于能及时交付。我们保留晚到记录，并研究只压缩重复引用身份的传输格式；不延长预算，也不由程序代写结论。

第03轮短动作任务解决了等待超时，各次请求均在90秒内返回；7次模型、13次工具、164.200秒，全部stop且7/7响应SHA与节点原始输出直接相同。模型仍将文献编号误当作参照器物编号，用空白和标点写竞争解释，证据合同拒绝生成报告。下一项修改是准确说明编号与已获引用资格的材料，不自动替它选择引用或写判断。这次失败保留在[实际第03轮记录](../verification/nvidia/compact-workflow-03/phase-trace.json)。

## 模型协作仍需专业验证

Spark承担原图视觉推理，StepFun只看公开或明确批准脱敏的文字，批准包先固定、再单次提交，不自动重试。真实本地模型接通后，还要做实际图像/局部/规划行为探针，冻结同模型、同资料、同预算的有无Skills对照，再由专家看图片和报告。3–5件专家样本是个案验证，不能据此声称行业准确率或保证获奖。

当前成果是受控试用的证据研究工作台。StepFun已完成一次真实公开文字适配器请求，但完整反证修订、独立专家质量、机构多用户权限、可信签署、实物检查、Spark性能优化和赛事视频仍须各自验收。设计细节与来源边界保存在 professional-research.md，部署验收在 spark-validation.md。

本轮新增无图文字凭据核查：只引用成功主动作实际接收的有限片段，正文回执另存字符范围和SHA；PDF不OCR。准备档案与离线交接包含历史事件所用旧版段落、原始照片与原文件清单；库中其它案卷与资料不进入交接。所有工程协议测试仍使用明示的合成夹具，不能推导专业鉴定成绩。

## 让首次体验真正完整

后续试用指出一个产品问题：评审打开系统后，如果还要自己找图片、上传多项材料、编写题目和关联资料，看到的只是待填表单，无法理解研究流程。我们因此准备了三套 Met 公开教学案，配齐实际照片、馆藏出处、项目原创文字说明、观察示例与补证路径，提供免上传的浏览器体验和本地完整教学导入。

教学材料与实时 AI 保持清楚区分。预写的意见标为项目编写的研究示例，浏览器实际完成编辑、证据定位、补证比较、复核备注和导出；它没有请求模型，不能剪成实时推理演示。GitHub Pages 只发布公开的 `site/`，真正的 Python 工具执行、私人材料和模型请求由本地 / Spark 后端完成。首次体验不依赖服务在线，实际推理仍必须凭真实运行证明。

公开仓库将README、七个方法包、来源权利、部署和工程验证整理成一个入口，并按官方六项评分列出实际证据。Spark真实计算、生成失败与修复、NVIDIA工具运行及StepFun文字探针分开记录；独立专家样本、完整反证闭环、B站视频、真实合影和正式表单仍须完成。完整教学网页不能替代这些材料。本篇仍是草稿，在赛事技术社区实际发表之后才有征文URL。

## 数字怎样才能有意义

用户希望一组照片自动得到详细报告与真品率。新版增加固定输入的逐图细节、支持与冲突依据、分项理由和下一项补证，并提供五类视角的采集覆盖指数。该指数来自上传者标注，不验证视角真实，也不表示真伪。真实性概率字段保持待校准。Jev的浏览器动作概率、Laya的文本路由概率和大模型的自报信心都不是陶瓷真品率；若没有定义真品目标、专家标签、独立校准集与外部分布拒判，数字再漂亮也没有解释基础。
